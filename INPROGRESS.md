# Process

## Starting from the brief

The [final project brief](https://comp.anu.edu.au/courses/comp4020-agentic-coding-studio/assessments/final-project/) asks for an app that is multi-user, real-time (changes propagate to other open sessions in about a second, no reload), and persistent across sessions, restarts and redeploys, deployed to a single Fly.io machine with one volume. It also asks for a definition of "good" that I make and defend myself, rather than one handed to me.

The repo ships with no starter app, just a placeholder that serves one page and `README.md` at `/readme/` [874688a](https://github.com/comp4020-agentic-coding-studio/comp4020-final-brendanmeyer/commit/874688aeed740ba499fa46a2e227ee12d52caab9). The stack, schema and interaction are entirely my own choice to make and justify here.

## First approach: a design document before any code

Rather than start writing the server, I wrote out the game design in full as `planning.md` [1c700a4](https://github.com/comp4020-agentic-coding-studio/comp4020-final-brendanmeyer/commit/1c700a4a5f9fd45a24ae1fd76575c73ae75862cb): a Snake variant where no single player controls the snake directly. Every active player controls a cursor, and the snake steers toward the centroid of all active cursors, weighted at exactly `1/n` per player. The design states this explicitly as the point: "the game therefore cannot meaningfully be played alone," which is a direct answer to the brief's multi-user requirement - multi-user isn't bolted on as an identity/session layer, it's the mechanic itself.

That first pass covered player identity, join/leave behaviour with a 2-second introduction window, a 12-player cap with lobby/spectator mode, no in-game chat (coordination happens through cursor movement), persistence of run history and a "ghost trail" of the record run, a first scoring model, and a server-authoritative simulation loop.

## Refining the scoring model

The first draft's participation scoring had an unresolved placeholder ("make the calcuation different for each play, so they cannot compare...") and left the group-size multiplier formula unspecified beyond "should increase gradually." That placeholder wasn't a considered position, just a marker that something had to go there so the first iteration was complete enough to react to - the actual rule came later.

The second pass [5aa3629](https://github.com/comp4020-agentic-coding-studio/comp4020-final-brendanmeyer/commit/5aa362971206c730e3bd2b72257f116d15d28bf0) resolved it:

- scoring was split into a **raw score** (snake progression only) and a **collective score** (raw × a group-size multiplier), computed **per food event** rather than once at the end of a run, specifically so a player joining late can't retroactively inflate points earned before they arrived;
- the multiplier was pinned to a concrete formula, `multiplier(n) = 1 + ((n - 2) / 10)^2`, an **increasing**-returns curve (going from 2→4 players barely moves the multiplier, but 10→12 does) rather than a diminishing-returns shape. This was deliberate, not a reinterpretation of "gradual": the goal is to incentivise bigger groups, and coordinating a large group with no chat is harder than coordinating a small one, so the reward for pulling it off should grow with the group rather than taper off;
- "active player" was given a single definition reused by both the centroid and the multiplier - joining/introduction, disconnected/flashing, and stale/timed-out players all explicitly don't count toward either.

## Expanding into identity, queueing and replay

The third pass [7bf1793](https://github.com/comp4020-agentic-coding-studio/comp4020-final-brendanmeyer/commit/7bf17932daf062f6430e00d5a4877feda433bc89) is substantially larger than the first two combined (600 insertions) and adds several subsystems the first draft didn't have:

- persistent accounts with an optional password (hashed, never stored plaintext, no reset flow) so a pseudonym can survive a browser session ending, not just a page refresh;
- a FIFO lobby queue with a 5-second claim window for the 13th-and-later visitor, replacing the first draft's unspecified "may enter the active game";
- a deterministic per-tick event order (connection state → active-player set → input → centroid → movement → collisions → scoring → spawn → broadcast), so a join or disconnect landing on the same tick as a food collection has a defined outcome instead of a race;
- ghost-trail replay of the record run at a fixed sample rate, and explicit rules that ties in the leaderboard resolve to whichever run reached the score first.

This reads as closing gaps the first two passes left implicit (what happens at the capacity boundary, what happens when two things occur on the same tick) by making the server-authoritative claim in section 12 of the original draft concrete enough to implement against. The motivation for going this far before writing any code was general rather than specific to this project: a well-thought-out base is worth having before starting, since it's what keeps the build on track rather than drifting as problems come up mid-implementation.

## Choosing what to build this week, not the whole design

`planning.md`'s 40 invariants are the full game; crit 8 only asks for proof of life. `CLAUDE.md` [eef072d](https://github.com/comp4020-agentic-coding-studio/comp4020-final-brendanmeyer/commit/eef072d) and `README.md` [0ec4f0c](https://github.com/comp4020-agentic-coding-studio/comp4020-final-brendanmeyer/commit/0ec4f0c) state, before any server code existed, what this week's slice actually commits to: real centroid steering and real scoring between two active sessions, a persisted per-visitor trace, and the 2-player minimum held from the first commit that has a game loop at all — invariant 40 explicitly bans a single-player fallback, so relaxing that minimum "temporarily" was never on the table. Everything else `planning.md` describes (passwords, the lobby queue, ghost trails, participation scoring, and more) is named and deferred rather than half-built.

New `spec/*.test.ts` checks were written against that scope next [bd39395](https://github.com/comp4020-agentic-coding-studio/comp4020-final-brendanmeyer/commit/bd39395), before the server code they test existed, and confirmed red for the right reason (nothing listening yet) rather than skipped past.

## Persistence: `node:sqlite` over a native driver

[`4398aa1`](https://github.com/comp4020-agentic-coding-studio/comp4020-final-brendanmeyer/commit/4398aa1) adds the DB layer on Node's built-in `node:sqlite` module (`DatabaseSync`) rather than `better-sqlite3`. The deciding factor was the Docker build: Fly's one machine has no separate database server, so everything durable lives in SQLite on the one mounted volume, and `node:sqlite` needs no native compilation step to get there — `better-sqlite3` would need node-gyp in the image for one dependency. The trade-off, recorded honestly rather than glossed over: Node's own docs still mark it "Stability: 1.2 — release candidate," not fully stable. That's mitigated by sticking to its narrowest, longest-settled surface (`exec`, `prepare().run/get/all`) and nothing more exotic.

## Schema: the smallest thing that can prove persistence

Three tables: `players`, `runs`, `run_players`. This is a strict subset of the ~20-field persistence model `planning.md` section 20 describes — no food event logs, no replay sampling, no participation records yet — and nothing in it needs to be migrated away later, only added to.

One addition beyond what was originally scoped: a `token` column on `players`, generated when a pseudonym is claimed and meant to be kept client-side (`localStorage`), because `GET /api/summary` needs a way to find *this* visitor's last run specifically, not just a global number — that's the difference between "a trace is still there" and "a counter went up somewhere."

## Server: plain `node:http` + `ws`, no build step

[`7b1bb70`](https://github.com/comp4020-agentic-coding-studio/comp4020-final-brendanmeyer/commit/7b1bb70) runs the server as `node src/server/index.ts` directly, rather than through a framework or a compiled output. Node 24.21 (pinned in `mise.toml`) has had type stripping stable since 24.12, and `tsconfig.json`'s own `allowImportingTsExtensions` comment was already pointing at exactly this. This week's server is a handful of routes plus one WebSocket upgrade ([`1a421e8`](https://github.com/comp4020-agentic-coding-studio/comp4020-final-brendanmeyer/commit/1a421e8)) — Express or Fastify would add a dependency tree and a routing abstraction the app doesn't need yet, for no benefit at this size. `ws` is the plain, widely-used WebSocket implementation; its optional native speed-up packages are allowed to fail silently on install, so it doesn't reopen the native-build problem the `node:sqlite` choice was specifically avoiding.

Real-time transport is a WebSocket, not polling or server-sent events, because the thing actually being proven this week — two sessions' cursor input converging into one steered snake ([`1b232b0`](https://github.com/comp4020-agentic-coding-studio/comp4020-final-brendanmeyer/commit/1b232b0)) — needs a bidirectional, low-latency channel; SSE has no client-to-server leg, and polling at the ~15Hz the loop ticks would be both laggier and wasteful.

## Client: a real build step, vanilla canvas

The server can skip a build step; the client can't, since browsers don't strip TypeScript types. [`bd39395`](https://github.com/comp4020-agentic-coding-studio/comp4020-final-brendanmeyer/commit/bd39395) scaffolds `tsconfig.client.json` (`NodeNext`, so source imports are written as the `.js` file the compiler will actually emit) to compile the client separately with `tsc`, emitting plain ES modules loaded directly via `<script type="module">` — no bundler. [`b890564`](https://github.com/comp4020-agentic-coding-studio/comp4020-final-brendanmeyer/commit/b890564) builds the client itself on that: a handful of draw calls per tick and no DOM tree to diff don't justify React or a game engine at this scale.

## Where this stands

The slice `CLAUDE.md` and `README.md` committed to is built and verified: [`eef072d...b890564`](https://github.com/comp4020-agentic-coding-studio/comp4020-final-brendanmeyer/compare/eef072d...b890564) takes the repo from a planning document to a server-authoritative game loop (centroid steering, collisions, the real `multiplier(n)` formula), a `node:sqlite`-backed persistence layer, a WebSocket handshake and game protocol, and a vanilla canvas client — with every step checked against the spec tests written for it before the code existed, and a manual two-client run confirming the full path end to end: waiting at one player, running at two, score rising correctly as food is eaten, and a wall collision finalizing a run that `GET /api/summary?token=...` then hands back correctly to that specific player. Still ahead: shipping the repo public and deploying it.

## Pre-crit-9 cleanup: two real bugs found by actually playing it

Before starting crit 9's own work, trying the deployed app surfaced two concrete problems a stranger would hit in the first few seconds, not hypothetical gaps.

The waiting screen said "open this page in another browser window" [`fb6f01d`](https://github.com/comp4020-agentic-coding-studio/comp4020-final-brendanmeyer/commit/fb6f01d8e919efa13f58829f50cf660e83e56475), which reads as "any new window" — so opening a second tab in the same browser was the natural thing to try. That doesn't work: the reconnect token lives in `localStorage`, shared by every tab on the same origin, so the second tab silently resumed the first tab's identity instead of claiming a new one. The copy now says what actually works — another browser, or a private/incognito window.

Mobile play was also cramped, since the on-screen canvas had to share the viewport with the browser's own address bar and toolbar chrome. [`01dec80`](https://github.com/comp4020-agentic-coding-studio/comp4020-final-brendanmeyer/commit/01dec80a7daf3dde8c7263f29ceda6948d9f53c9) added a header button toggling the Fullscreen API on the whole page (not just the canvas, so the score stays visible), feature-detected so it stays hidden where the API doesn't exist.

## Making the same-identity bug impossible, not just mislabelled

The copy fix in `fb6f01d` explained the localStorage sharing problem but didn't stop it from happening if someone opened a second tab anyway. The actual fix needed to be server-side: the server is already the authority on identity, so it's the one place that can actually know whether a token already has a live connection, regardless of which tab, browser, or device asks.

[`526f921`](https://github.com/comp4020-agentic-coding-studio/comp4020-final-brendanmeyer/commit/526f92152137f1f292e0d7fceced6488f8c51e89) wrote `spec/duplicate-tab.test.ts` and the protocol shapes it needs (`takeover` on the hello message, a new `alreadyConnected` reply) before `ws.ts` did anything differently, confirmed red for the right reason: the server answered `welcome` both times, since nothing yet distinguished a genuine returning visitor from a second live tab. [`103aec3`](https://github.com/comp4020-agentic-coding-studio/comp4020-final-brendanmeyer/commit/103aec3c9f872341fd9bbc032b821cbec5f4a4bb) made it green: a resumed token that already has a live connection gets offered a takeover instead of being silently registered as a second connection for the same identity; confirming the takeover deletes the old connection from the map before closing its socket, so no tick can ever see both as live for the same player. [`7150e41`](https://github.com/comp4020-agentic-coding-studio/comp4020-final-brendanmeyer/commit/7150e41da1b951d78f8a468e4dbffbc59d3c892a) wired the client side: a plain `confirm()` asking whether to take over, and a status message for the tab that gets kicked, so it explains itself instead of freezing silently on its last frame. This was a specific design choice among the ones available (reject outright, kick silently, or ask) — ask-then-kick was picked so a deliberate device switch works without surprising anyone still using the original tab unknowingly.

## Testing DOM logic that isn't an HTTP check

`spec/README.md` scopes `spec/` to checks against the running app over HTTP/WS, which is what every test there had been until now. The fullscreen toggle is pure DOM logic with no server round trip at all, so it didn't fit that shape cleanly — the first attempt put it in `src/client/fullscreen.test.ts` instead, widening `vitest.config.ts` to pick up a second test location.

That split was wrong: one project should have one place tests live, not a rule explaining why some don't. [`ea0e79f`](https://github.com/comp4020-agentic-coding-studio/comp4020-final-brendanmeyer/commit/ea0e79fa1d7a8385e80351b8d06fc9c176b8bfee) moved the still-red test into `spec/fullscreen.test.ts` and reverted `vitest.config.ts` back to only ever looking there; a test that needs a browser DOM rather than a running server now says so locally, with a `// @vitest-environment jsdom` comment on just that file, instead of the whole suite's config branching on where a file happens to sit. [`f192322`](https://github.com/comp4020-agentic-coding-studio/comp4020-final-brendanmeyer/commit/f192322bf1bb0e7517fb805dce81f9a92753e046) is the test itself, confirmed red because `src/client/fullscreen.ts` didn't exist yet — the toggle had originally been written inline in `main.ts`, which opens a real WebSocket on import and so can't be unit-tested directly. [`e22cef7`](https://github.com/comp4020-agentic-coding-studio/comp4020-final-brendanmeyer/commit/e22cef75c579946fccae51982a9c5b4b025389a9) extracted it into its own module taking the host `Document` as a parameter, which is what let the test drive it through a fake instead of fighting jsdom's lack of a real Fullscreen implementation. `pnpm check` is green against the actual current code, including the always-running local dev server on port 8080, which needed restarting mid-session since `node` doesn't pick up `.ts` edits without one.

## Scoping crit 9 and writing down the identity decision

`CLAUDE.md` gets a crit 9 section the same way it got a crit 8 one before any of that week's code existed: real-time has to hold on the deploy itself, not just in local tests, and one documented multi-user decision has to exist and be defensible out loud, including the alternative that was rejected.

The decision turned out to already be sitting in the work just finished, not something to invent separately: what does a player's identity mean when their connection changes. Two sub-cases cover it. The first is the duplicate-tab bug just fixed — a second connection while the first is still live, now answered with a takeover offer rather than a silent double-up or a silent kick. The second is the plain case `planning.md` §5 designs in full: the first connection actually goes away and the token is used again later. That fuller design (a 3-second timeout, a flashing cursor, re-entry through a queue) stays deliberately unbuilt this week — a 2-player game has no capacity problem for a queue to solve yet, and reaching for that machinery now just because the file is already open would be exactly the scope creep `CLAUDE.md` warns against.

`decisions/0001-identity-across-connection-changes.md` records both halves together with the alternatives rejected for each: doing nothing (lets one visitor's own tabs count as several players toward the scoring multiplier), rejecting the new connection outright (locks out an ordinary device switch with no way back in), and kicking silently (leaves the original tab frozen with nothing on screen explaining why) — all weighed against `README.md`'s own "good" bar rather than an abstract preference. `README.md` is brought back into alignment with it: real-time and the takeover behaviour are now things a visitor is told about rather than just things that happen.

## Overriding the deferral: building planning.md's full disconnect-timeout/queue system

The section above records a deliberate choice not to build colours, the capacity cap, the queue, or ghost trails this week. That choice got explicitly overridden immediately afterward — asked for directly, twice, including after being told it entangles with other already-deferred features (ghost trail, global stats) and reverses the ADR just written. `decisions/0001`'s Case 2 answer flips from "resume immediately, no timeout, no queue" to the opposite — the full `planning.md` §5 design — since once a queue exists at all, an unconditional instant resume would let a reconnecting visitor skip it entirely [`6b35d3e`](https://github.com/comp4020-agentic-coding-studio/comp4020-final-brendanmeyer/commit/6b35d3e249ec2b807c18a7210edabcd3892ac369). `CLAUDE.md` gets a new crit 10 scope section rather than rewriting crit 8/9's, which stay as the historical record of what those weeks actually scoped [`7889658`](https://github.com/comp4020-agentic-coding-studio/comp4020-final-brendanmeyer/commit/7889658ee9ad793f9d6ea37cc5fdf2f161ee55e8).

Given the size of what was being asked — colours (§2), join-intro (§4), disconnect/reconnect (§5), the 12-player cap and spectator mode (§6), the FIFO queue (§7), leaderboard ties (§19), ghost trails (§21), and global stats (§22) — this went through full plan-mode research (two parallel exploration passes over the existing code and over `planning.md`'s exact text, then a dedicated planning pass) before any of it was written, rather than improvising section by section. The resulting plan sequenced eight phases so that stopping at any phase boundary would leave the repo fully working and fully tested, never half-built, with the two biggest unknowns (the queue's state space, and ghost-trail replay's dependence on an actual played-to-completion game) placed last rather than first.

### Phase 1: role scaffolding, and a small aside

`GameState` gains `pausedWithRun` [`2c04525`](https://github.com/comp4020-agentic-coding-studio/comp4020-final-brendanmeyer/commit/2c04525) [`6694ffc`](https://github.com/comp4020-agentic-coding-studio/comp4020-final-brendanmeyer/commit/6694ffc) to distinguish "never started" from "was running, then dropped below 2 players" — needed so the join-intro flash and the paused-game resume countdown don't both collapse into the already-tested "two fresh sessions start immediately" path. `Connection` gains `role`/`roleChangedAt`/`lastActivityAt`/`colorIndex`, everyone defaulting to `"active"` with zero behaviour change, checked by re-running the entire existing suite — including the takeover path — as an explicit regression gate.

Mid-build, a one-line request ("hide the snake when the game is in a paused state") turned into its own small test-first slice: `StateMessage` gains `pausedWithRun` too (reversing an earlier plan note that it would stay server-only), and `render.ts`'s new `shouldDrawSnake()` keeps the snake visible at its starting position for a never-started wait but hidden for a paused one [`33664d3`](https://github.com/comp4020-agentic-coding-studio/comp4020-final-brendanmeyer/commit/33664d3) [`9f8fecd`](https://github.com/comp4020-agentic-coding-studio/comp4020-final-brendanmeyer/commit/9f8fecd).

### Phase 2: disconnect timeout, and a test-design correction

The plan's own suggested test — abrupt `ws.terminate()` vs clean `.close()` — turned out not to actually test what it claimed to: on localhost, destroying a socket still tends to deliver a close to the server almost immediately, so both paths would hit the same code. The pure 3-second-timeout/2-second-flash threshold logic (`roles.ts`'s `nextRole`) is tested instead with fabricated timestamps, no real waiting or network simulation needed; the real-socket test covers only the half a real socket can actually prove — that a clean close is wired through to the leaving flash immediately, not after waiting out the silence timeout [`b486e9e`](https://github.com/comp4020-agentic-coding-studio/comp4020-final-brendanmeyer/commit/b486e9e) [`5adb45c`](https://github.com/comp4020-agentic-coding-studio/comp4020-final-brendanmeyer/commit/5adb45c). A 1-second ping heartbeat plus `markActivity()` on input and pong is what actually lets a silent drop be noticed at all — an idle-but-connected player never times out, only one that stops answering pings.

### Phase 3: colours

`colors.ts` reserves/releases palette indices through an explicit state object rather than module globals, the same pattern `queue.ts` would need later [`0e37af6`](https://github.com/comp4020-agentic-coding-studio/comp4020-final-brendanmeyer/commit/0e37af6) [`ff67007`](https://github.com/comp4020-agentic-coding-studio/comp4020-final-brendanmeyer/commit/ff67007) [`7cd8acd`](https://github.com/comp4020-agentic-coding-studio/comp4020-final-brendanmeyer/commit/7cd8acd). One test bug surfaced and got fixed while making it green: asserting an exact low colour index collided with whatever index a *different* test's unnamed connections happened to grab first, since those always take the lowest free one — fixed by asserting against high indices instead, which stay clear of that traffic.

### Phase 4: join-intro, and a dependency-direction fix

Deciding a newly-registered connection's role needs to read the current game status — but `ws.ts` already exports `connections`/`sweep` to `loop.ts`, so `ws.ts` importing a status-getter back from `loop.ts` would be circular. `state.ts` becomes the single owner of the mutable `GameState` (`getState`/`setState`) instead of a private variable inside `loop.ts`, so both modules can read it without importing each other [`ef1da80`](https://github.com/comp4020-agentic-coding-studio/comp4020-final-brendanmeyer/commit/ef1da80) [`df71260`](https://github.com/comp4020-agentic-coding-studio/comp4020-final-brendanmeyer/commit/df71260) [`bd37a92`](https://github.com/comp4020-agentic-coding-studio/comp4020-final-brendanmeyer/commit/bd37a92).

This is also where a real, structural cross-test problem first surfaced: once a paused run is a real, correct, persistent thing (not a bug), any WS test that gets two players running and then disconnects leaves the shared dev server in that paused state for whichever test runs next — and vitest's actual file execution order turned out not to be alphabetical or otherwise predictable, so no file could assume what ran immediately before it. Trying to have each test "clean up" its own mess just moved the same pause to the next file in sequence and never terminated. The fix that actually works: every WS test that waits for two sessions to reach active tolerates *either* immediate activation or an inherited resume countdown, since both are correct outcomes and the test only needs the game to get there, not to control which path it takes.

### Phase 5: the capacity cap, and `you` becoming personal

Beyond the 12-player cap, `admit()` overrides whatever `activateRole` alone would have decided, becoming `"spectator"` instead [`72c21b8`](https://github.com/comp4020-agentic-coding-studio/comp4020-final-brendanmeyer/commit/72c21b8) [`d6f701f`](https://github.com/comp4020-agentic-coding-studio/comp4020-final-brendanmeyer/commit/d6f701f) [`6de50d0`](https://github.com/comp4020-agentic-coding-studio/comp4020-final-brendanmeyer/commit/6de50d0). A spectator has no cursor and so no entry in `players` at all, which means `StateMessage` needs a personalized `you` field just so a spectator can learn its own standing — the one field `broadcast()` can't compute once and share across every socket's payload; it now builds one message per recipient instead of one shared payload for everyone.

### Phase 6: the FIFO queue — the plan's own highest-risk phase

`queue.ts`'s `enqueue`/`makeOfferIfNeeded`/`accept`/`dropOffer`/`expireIfNeeded` as an explicit state object, tested with fabricated timestamps the same way `roles.ts` was [`5e40a44`](https://github.com/comp4020-agentic-coding-studio/comp4020-final-brendanmeyer/commit/5e40a44) [`0c11b0d`](https://github.com/comp4020-agentic-coding-studio/comp4020-final-brendanmeyer/commit/0c11b0d). `requestJoin` is opt-in — a spectator only enters the queue by explicitly asking, never automatically — matching the spec's "a declined/expired offer sends you behind currently-waiting spectators if they request to join again," which only makes sense as a repeatable, deliberate action [`022eeb0`](https://github.com/comp4020-agentic-coding-studio/comp4020-final-brendanmeyer/commit/022eeb0) [`796a0cf`](https://github.com/comp4020-agentic-coding-studio/comp4020-final-brendanmeyer/commit/796a0cf). Accepting an offer reuses the exact same `activateRole` decision a direct join uses, rather than a separate code path, so queue-acceptance and ordinary joining can't drift apart. Despite being flagged the riskiest phase in the plan, this landed cleanly on the first real attempt — the largest state space in the whole build, but one the earlier phases' patterns (explicit state objects, pure decision functions, personalized `you`) already had answers for.

### Phase 7: leaderboard ties and global stats — the schema-migration risk, for real

`sortRecords`/`isNewRecord` as pure functions specifically so an exact score tie can be hand-constructed, since producing one through real gameplay isn't practical [`c56e5bf`](https://github.com/comp4020-agentic-coding-studio/comp4020-final-brendanmeyer/commit/c56e5bf) [`b8ee864`](https://github.com/comp4020-agentic-coding-studio/comp4020-final-brendanmeyer/commit/b8ee864). The real risk here was named before any code was written: `CREATE TABLE IF NOT EXISTS` does nothing to a table that already exists, and the production Fly volume's `runs` table has existed since crit 8 — new columns need genuine `ALTER TABLE` statements, applied idempotently, which neither CI nor local `pnpm check` would ever catch getting wrong since both start from an empty database. `schema.ts`'s `applySchema()` checks `PRAGMA table_info` before altering, proven against a throwaway `DatabaseSync` built to look like an already-deployed table, not the app's own singleton [`37242a8`](https://github.com/comp4020-agentic-coding-studio/comp4020-final-brendanmeyer/commit/37242a8) [`693161a`](https://github.com/comp4020-agentic-coding-studio/comp4020-final-brendanmeyer/commit/693161a). `recordRun()` now checks the prior best *before* inserting, so a run's own score can never count as its own previous best, and returns whether it was a record alongside the row id [`25e34df`](https://github.com/comp4020-agentic-coding-studio/comp4020-final-brendanmeyer/commit/25e34df) [`1e1549b`](https://github.com/comp4020-agentic-coding-studio/comp4020-final-brendanmeyer/commit/1e1549b).

### Making it visible

After seven phases of server logic — every bit of it correct and tested — none of it was visible to an actual player: `render.ts` still drew one hardcoded colour for everyone, there was no way to even choose a colour, no flash, no queue UI. Forcing that real collision also finally exercised a code path nothing before it ever had: a finished run holds `status: "gameover"` for a full 5-second `GAME_OVER_RESET_MS` before resetting. `spec/settle.ts`'s shared cross-test buffer — built during Phase 4/5 to cover a closed socket's 2-second leaving flash — didn't cover a 5-second gameover window, so the one test that forces a collision could leave the shared server busier than any other file expected for longer than they waited out. The buffer grows from 2.5s to 6s, and every file using it gets a matching timeout bump, rather than treating the gap as a one-off flake to retry past.

## Crit 9 preflight: five real bugs found by running the checklist, two deliberate scope overrides

### Live-URL spec failures: margins, not defects

A crit-9 submission preflight pass checked the spec suite against the actual deployed URL, not just CI's own throwaway container — something nothing in the regular workflow does. 4 of 25 spec files failed live that passed everywhere else. `colors-ws.test.ts`'s and `duplicate-tab.test.ts`'s failures were margin problems (hardcoded palette indices colliding with real connections already holding them; a plain 5-second default timeout too tight for real WAN latency to the Fly `syd` region), fixed by anchoring on whatever colour the server actually assigns instead of a literal index, and a generous timeout. `disconnect-timeout.test.ts` was asserting an exact `activeCount`, which a server with other real connections can never guarantee — switched to tracking the delta its own connection causes instead [`8c1db57`](https://github.com/comp4020-agentic-coding-studio/comp4020-final-brendanmeyer/commit/8c1db57a92fd386d0893334c5662548db65460ff). ## Crit 10: the real published spec, pulled from the course site

Before writing anything, the actual crit 10 spec was fetched live from `comp4020-agentic-coding-studio/crits/10-fly-by-instruments` rather than assumed from `CLAUDE.md`'s existing "crit 10 scope" heading. That heading describes the disconnect-timeout/queue/colours/ghost-trail/stats system, which was built early as a deliberate scope override during the crit 9 session, before this week's real spec was published. The two are unrelated: this week's actual bar is that the app logs who did what, server-side, with logging that survives past the crit itself; that what each person may see or change is checked on the server and that decision is written down with why; and that at the crit, two pod members use the deployed app directly from its URL while the presenter narrates entirely from the logs (`flyctl logs`), never touching the UI themselves. `CLAUDE.md`'s existing crit 10 section is left exactly as it is — it's an accurate record of real, shipped work — rather than rewritten to match a spec that didn't exist when that work was scoped.

### Auditing before building

Before writing an ADR or any enforcement code, the existing protocol in `src/server/ws.ts` was read end to end to check whether a real permission gap existed at all. It doesn't: no `ClientMessage` shape the server accepts carries another player's ID, so every handler already resolves "who is this" from the live socket's own entry in the `connections` map and can only ever act on that connection's own identity. The one place "whose data is this" genuinely matters is `GET /api/summary?token=`, already gated by possession of an opaque per-player token never sent to anyone but its owner. `decisions/0002-server-side-permission-checks.md` [`193d03b`](https://github.com/comp4020-agentic-coding-studio/comp4020-final-brendanmeyer/commit/193d03b) writes this down in the same Context/Decision/Alternatives/Trade-off shape as `decisions/0001`: the protocol's own shape is the enforcement, not a checked-but-fallible permission gate bolted on afterward, and a full account/role system was rejected as machinery with nothing to protect at this app's size.

### Test-first: a failing spec before any logging code existed

`spec/events.test.ts` [`dcac976`](https://github.com/comp4020-agentic-coding-studio/comp4020-final-brendanmeyer/commit/dcac976) was written and confirmed red first — `src/server/log.ts` and `db/repo.ts`'s `insertEvent`/`listEvents` didn't exist yet, so the import itself failed, for the right reason. It asserts three things: the `events` table gets created by `applySchema` and stays idempotent; `insertEvent`/`listEvents` round-trip in reverse-chronological order with JSON `details` parsed back out; and `formatEvent`, a pure function with no DB or socket involved, produces a distinguishable line for every event type this build logs, directly encoding the crit's own named failure condition — being unable to tell two classmates apart in the logs.

### The events table and logEvent, making the spec green

`events` is a brand-new table, unlike `runs`/`players`, so `CREATE TABLE IF NOT EXISTS` is the whole migration story — no `ALTER TABLE` risk this time [`ba3f30d`](https://github.com/comp4020-agentic-coding-studio/comp4020-final-brendanmeyer/commit/ba3f30d). `insertEvent`/`listEvents` take an explicit `DatabaseSync` parameter rather than closing over `repo.ts`'s module-level singleton, the same shape `schema.ts`'s own `applySchema` already uses, specifically so the spec can exercise them against a disposable temp-file database instead of the app's real one. `src/server/log.ts`'s `logEvent` does two things on every call: a `console.log` line (what a crit presenter tails live with `flyctl logs -a <repo>`) and an `insertEvent` against the real database (what makes the log outlive the crit session, since the one Fly volume at `/data` is this app's only durable store). `pnpm check` went green at 28 files / 99 tests with this commit, with the actual call sites still unwired.

### Wiring every call site, verified against a real running server

`src/server/ws.ts` and `src/server/game/loop.ts` [`b841d4a`](https://github.com/comp4020-agentic-coding-studio/comp4020-final-brendanmeyer/commit/b841d4a) call `logEvent` at every identity, queue, role, and scoring transition: claiming a name (and distinguishing a fresh claim from a token resume from a password-based retrieval), renaming, duplicate-tab detection, a confirmed takeover, a clean disconnect versus a silent timeout, every `role_changed` transition `sweep()` applies plus the ones the direct message handlers assign, the FIFO queue's join/offer-made/declined-or-expired, each food pickup, and a finished run. A `role_changed` to `"removed"` deliberately doesn't also log a second `player_disconnected` — that event already fired the moment the connection first went silent or closed, and `"removed"` is just the leaving flash's window finishing, not a new disconnect.

No new HTTP route was added for reading the log back. The published spec asks only that the app log server-side and that the logging survive past the crit — `console.log` plus the durable `events` table already satisfy both halves exactly, and a `GET /api/events` endpoint would be new public surface with nothing in the spec asking for it. This does narrow what `pnpm check` alone can prove: the schema, the repo round-trip, and the formatter are all directly unit-tested, but that `ws.ts`/`loop.ts` actually call `logEvent` at the right real-world moments isn't something an external HTTP/WS spec file can check without a read-back route. That gap was closed manually instead — two real WebSocket clients were driven through claim, rename, a duplicate-tab hello, and disconnect against the actual running dev server, with the resulting `console.log` output read back to confirm it names the right player by name at every step, distinguishably, and reads as a coherent narration end to end. `pnpm check` stayed green (28 files, 99 tests) after the wiring, with no regressions.

### A real bug found by direct request, not by the preflight checklist

Asked directly to check password protection: "the password protection of an account (id/name) is not working... you may need to check the db for id's that fail these." Name uniqueness itself was never actually broken — a `UNIQUE` constraint on `players.name_lower` already prevents duplicate names at the database layer, confirmed clean on both the local dev DB and, at the user's explicit follow-up ("the live db too"), the real production database via `mise exec -- flyctl ssh console`: zero duplicate `name_lower` rows and zero password hash/salt inconsistencies in both.

The real bug was in request resolution, not data: `findExistingPlayer` (`src/server/db/repo.ts`) resolved a hello's token unconditionally, before ever checking a typed name or password. `src/client/net.ts`'s `sendHello` always attaches whatever token the browser already has on every hello, regardless of what name was typed into the entry box — so a visitor whose browser already held any token at all, even a stale, unrelated, auto-generated pseudonym from an earlier visit, could never retrieve a different, password-protected account, correct password or not. The server silently kept resuming the old, unrelated identity instead. This was reproduced directly against the running local server with disposable WebSocket clients before writing any test or fix, confirming the exact failure first-hand rather than guessing from reading the code.

`spec/password.test.ts` [`1681e5d`](https://github.com/comp4020-agentic-coding-studio/comp4020-final-brendanmeyer/commit/1681e5d) got two new cases, confirmed red for the right reason against the real bug: a correctly-password-proven retrieval request must win even when it also carries an unrelated token, and a wrong password must never resolve to someone else's protected identity regardless of what token is attached. `findExistingPlayer` [`44874ea`](https://github.com/comp4020-agentic-coding-studio/comp4020-final-brendanmeyer/commit/44874ea) now checks a correctly-password-proven name first — proof that can't happen by accident, so it's treated as the more deliberate signal — before falling back to an ordinary token resume, and only after that to the existing, already-tested "keep your current name on an unprotected collision" behaviour, which is unchanged. `pnpm check` stayed green (28 files, 101 tests) with no regressions, including every existing duplicate-tab and pseudonym spec.

Still ahead: `reflections/crit-10.md` once there's a real breakthrough worth writing about.

### Adding a password after claiming with none

Asked directly for an option to add a password to an already-connected account that doesn't have one. `src/shared/protocol.ts` gained `SetPasswordMessage`/`PasswordSetMessage` [`11958d6`](https://github.com/comp4020-agentic-coding-studio/comp4020-final-brendanmeyer/commit/11958d6) — no target player id in the message at all, consistent with `decisions/0002`'s finding that nothing in this protocol can name another player, and this isn't the exception. `spec/password.test.ts` got three new cases first, confirmed red because the server had no handler for the new message type yet and silently ignored it: setting a password on a password-less identity, then confirming the old any-password behaviour stops working for it immediately after; refusing to set one on an identity that already has one, without overwriting the original; and refusing a blank password outright, since that's just the existing no-password default rather than something to explicitly request.

`setPasswordIfNone` [`a281841`](https://github.com/comp4020-agentic-coding-studio/comp4020-final-brendanmeyer/commit/a281841) enforces "only when currently none" directly in the `UPDATE`'s own `WHERE password_hash IS NULL` clause, so there's no separate read-then-write race between checking and setting it. `ws.ts`'s handler operates only on `connections.get(socket)`'s own entry, the same shape as every other handler. Writing the new specs surfaced a latent raciness nothing earlier had hit: a connection that's been open for a while (as these now are, past their initial hello) can have a `state` broadcast land between a request and its reply, since the game loop ticks independently — `nextMessageOfType` was added to skip past those rather than asserting on whatever happens to arrive next.

The client got a "Protect this name" control in the header, shown once connected [`2baedd8`](https://github.com/comp4020-agentic-coding-studio/comp4020-final-brendanmeyer/commit/2baedd8). The client has no way to know in advance whether its identity already has a password, so the control is just always offered rather than guessed at — the server's reply (success, or "already has one") resolves the question for that session. Manually verified end to end against the real running server with disposable WebSocket clients, mirroring exactly what the UI sends: claim with no password, set one, a second attempt correctly refused, a subsequent wrong-password retrieval rejected, and the newly-set password retrieving the identity correctly. `CLAUDE.md` and `README.md` [`46a27b1`](https://github.com/comp4020-agentic-coding-studio/comp4020-final-brendanmeyer/commit/46a27b1) were brought up to date in the same spirit as the original password feature's own documentation — an existing password still can't be changed or recovered, only added where there wasn't one before.

`pnpm check` stayed green throughout (28 files, 104 tests after the server-side commit, same count after the client-only commit since it adds no new spec), typecheck and the client build both clean.

### Replacing the always-offered control with a themed dialog the server can gate

The "Protect this name" control's own writeup above already named the thing it was missing: the client had no way to know in advance whether an identity already had a password, so the button was always shown and a refusal only resolved the question after the fact. Closed that gap properly instead of leaving it as a known rough edge. `src/shared/protocol.ts`'s `WelcomeMessage` gained `hasPassword: boolean` with failing specs/types first [`719a95d`](https://github.com/comp4020-agentic-coding-studio/comp4020-final-brendanmeyer/commit/719a95d) — confirmed red via typecheck, since both welcome call sites in `ws.ts` were missing the new required field. Fixing the new specs surfaced one real resume-timing lesson: a clean socket close doesn't drop a connection immediately, it starts the 2s leaving flash `decisions/0001` already documents, so a same-token resume right after a close still needs `takeover: true`, same as every other resume-after-close case in the file — not a new race, just a case the existing rule already covered.

### Hiding the password field once already "logged in", and a deliberate way to stop being

The entry screen's password field exists for exactly one purpose — retrieving a name from a device that doesn't already hold its reconnect token — so a returning visitor whose browser already has one has nothing for it to do, and showing it anyway just invites a pointless, ignored retype. `spec/entry.test.ts` got the failing case first [`9c17a36`](https://github.com/comp4020-agentic-coding-studio/comp4020-final-brendanmeyer/commit/9c17a36), confirmed red against a plain `collectEntry` that never looked at storage at all. The fix is a one-line check in `entry.ts`: `passwordInput.hidden = getStoredToken() !== undefined`, reusing `net.ts`'s own token accessor rather than re-reading `localStorage` directly.

The matching other half: `planning.md`'s "explicitly starting a new login/session creates a new browser session" names an action this build never actually offered on purpose — the only existing path to a fresh identity was declining a takeover offer, a side effect of a flow most visitors never see. Added a "Change user" button to the header, shown from the same point `setPasswordBtn` already is (a confirmed identity), that calls the same `clearStored()` + `location.reload()` pair already used by that decline path. No new spec for the click handler itself — `main.ts`'s existing button wiring (fullscreen, the queue buttons, set-password) has none either, verified instead by the protocol-level specs that already exercise a cleared identity claiming fresh (`spec/duplicate-tab.test.ts`'s own "not this identity" path). `pnpm check` green: 30 files, 113 tests, typecheck and client build both clean.

### Turning the stats page into a dialog, with one real decision about where closing it goes

Asked directly to make `/stats.html` a dialog over the game like `dialog.ts`/`passwordDialog.ts` already are, with a specific rule for what closing it should do: back to the game if still playing, to the entry screen if the connection was already gone. `statsDialog.ts` [`7c3bdce`](https://github.com/comp4020-agentic-coding-studio/comp4020-final-brendanmeyer/commit/7c3bdce) carries `stats.ts`'s `loadStats`/`loadRecords`/replay-loop logic across basically unchanged — the actual rendering was never the risky part — now driven through `showStatsDialog`'s open/close lifecycle instead of running once at page load. ### Auditing planning.md itself, and starting on what it finds

A fork audited `planning.md` section by section against the actual codebase — not a crit scope check (`CLAUDE.md` already governs that), but the fuller design document underneath it. Two of five findings turned out to already be covered by other mechanisms and were dropped at the user's direction (a distinct browser-session ID, and average active player count); three were genuine, never-deferred gaps: section 11's centroid visibility/easy-hard mode, section 12's random speed-or-growth progression, and section 13's multi-food spawning. Planned all three together, in increasing order of footprint, before starting any of them.

### Centroid visibility (easy/hard mode)

First of the three. `spec/centroid.test.ts` [`f98ea72`](https://github.com/comp4020-agentic-coding-studio/comp4020-final-brendanmeyer/commit/f98ea72) went in first, confirmed red via typecheck — `StateMessage` had no `centroid` field for the test to read. `loop.ts` already computed the centroid internally every tick just to steer the snake (`centroid.ts`'s plain mean over the active set); `broadcast()` [`6842c67`](https://github.com/comp4020-agentic-coding-studio/comp4020-final-brendanmeyer/commit/6842c67) now puts that same value on the wire, `null` whenever there's no active player to average, mirroring how `food` was already nullable.

Section 11 is explicit this is a **local display setting**, never shared simulation state — the client never sends a toggle back to the server, so there's no protocol message for it at all, just a plain boolean in `main.ts` toggled by `C` the same way `G` already toggles the ghost trail. Defaulted to visible (easy mode) rather than hidden, since `README.md`'s own bar is a first-time visitor understanding the game from what's on screen alone, and showing where the group is steering serves that more directly than hiding it by default would. `render.ts`'s `draw()` gained an optional `showCentroid` parameter (default `true`) drawing a small crosshair-in-a-circle, visually distinct from the filled player-cursor dots. No DOM spec for the `C` keydown handler itself, same precedent as `G`'s existing handler — it's wiring, not logic. `pnpm check` green: 32 files, 119 tests (one `disconnect-timeout.test.ts` failure seen once was confirmed transient — passed standalone and on a clean full rerun — cross-file shared-state contention per `spec/settle.ts`'s own documented risk, not a regression).

### Progression: a random speed-or-growth choice per food pickup

Second of the three audit findings. `spec/progression.test.ts` [`441ffb5`](https://github.com/comp4020-agentic-coding-studio/comp4020-final-brendanmeyer/commit/441ffb5) went in first, confirmed red because `src/server/game/progression.ts` didn't exist — every pickup had always just grown the snake by a fixed amount, with no random choice and no speed path at all.

`pickProgression(rng)` [`6d2aff2`](https://github.com/comp4020-agentic-coding-studio/comp4020-final-brendanmeyer/commit/6d2aff2) takes an injectable `rng` rather than calling `Math.random` itself — the same thing `food.ts`'s `spawnFood` already did inline for its own randomness, just made explicit and testable here — so both the "speedUp" and "grow" branches are deterministic in the spec instead of asserted on a statistical distribution. `state.ts`'s `GameState` gained `snakeSpeed`, replacing the old hardcoded `SNAKE_SPEED` constant in `loop.ts`'s head-advance calculation; every run still starts at the same base speed via `freshState`, and only a "speedUp" pickup ever moves it, through `applySpeedCap`'s cap at twice the starting speed. The two bonuses are now mutually exclusive per planning.md's wording — "a growth **or** speed increase," not both landing on every pickup the way it worked before. The existing `food_eaten` audit-log event picked up a `progression` field for free, since the roll already happens right where that event is logged.

`pnpm check` green: 33 files, 123 tests, typecheck and client build both clean. No live-server spec for the random choice itself, same reasoning `spec/roles.test.ts` already gives for preferring fabricated inputs over real elapsed time — pinning exact snake length against a real forced wall-collision run would make an existing test brittle for no real coverage gain over the pure unit tests.

### Multi-food spawning, and a real bug found while testing it live

Last of the three audit findings, and the one touching the most surface area: `food: Vec2 | null` across `state.ts`/`protocol.ts`/`render.ts` becomes `Vec2[]`. `spec/food.test.ts` [`bb7c02c`](https://github.com/comp4020-agentic-coding-studio/comp4020-final-brendanmeyer/commit/bb7c02c) went in first, confirmed red because none of `pickFoodCount`/`topUpFood` existed and `eatsFood`'s signature didn't match an array.

`pickFoodCount` [`4645147`](https://github.com/comp4020-agentic-coding-studio/comp4020-final-brendanmeyer/commit/4645147) implements planning.md's weighted distribution (`weight(k) = 1/2^(k-1)`, normalized, picked via an injectable `rng` — the same pattern `progression.ts`'s `pickProgression` already established, for the same reason: exact boundaries testable without relying on real randomness landing where a test needs it). `spawnFood` now also rejects candidates colliding with other existing food, not just the snake. `eatsFood` returns whichever item was actually eaten (or `null`) so `loop.ts` can remove just that one rather than clearing the whole board.

Writing `spec/multi-food.test.ts` — the one live-server check for this feature, confirming `state.food` stays an array within `[0, activeCount]` against a real running game — caught a real gap the pure unit tests alone hadn't: `topUpFood` only ever adds, so when an earlier test file's larger group had spawned several food items and this test's smaller 2-player run inherited the shared server's leftover state, the board still had more food than 2 players should ever see. Section 13's "maximum number of food items is the number of active players" is a hard cap, not just a spawn-time target — it needs enforcing independent of whether a pickup just happened, since the active set can shrink from a disconnect alone. Fixed test-first: corrected `spec/food.test.ts`'s own wrong assumption (a test had asserted `topUpFood` should leave a 3-item board at 3 even when only 2 players remained) before adding `capFood`, applied every tick in `loop.ts` ahead of every other food decision, separately from `topUpFood`'s weighted re-roll which only happens alongside an actual pickup so an idle board's count doesn't drift on its own between pickups.

`pnpm check` green: 35 files, 136 tests, typecheck and client build both clean. One of the two live-server test runs that led to this fix needed the local dev server restarted mid-session before it would actually exercise the new `loop.ts` code — the same standing risk this repo's process notes already call out for client-only changes, holding again here for server changes made while an old server process was still running.

### A periodic positions line for the audit log

Asked directly for one: a log line naming every active player and their current position, every 30 seconds while a game is actually being played — something between crit 10's existing transition events for a presenter narrating from `flyctl logs` to point at. `spec/positions-log.test.ts` [`aacd674`](https://github.com/comp4020-agentic-coding-studio/comp4020-final-brendanmeyer/commit/aacd674) went in first, confirmed red against a nonexistent module.

Wired into `loop.ts`'s `tick()` [`0935c91`](https://github.com/comp4020-agentic-coding-studio/comp4020-final-brendanmeyer/commit/0935c91) right after the active-player set is known, reusing the same `active` list the tick's own centroid/scoring already computed. `lastPositionsLoggedAt` resets to `null` on the waiting→running transition alongside every other per-run counter, so a fresh run always gets its first snapshot immediately rather than waiting out a stale interval from whatever ran before it.
